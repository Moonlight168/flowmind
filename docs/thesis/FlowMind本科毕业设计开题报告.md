# 一、课题基本信息

## 1.1 课题名称

基于大语言模型的智能流程审批系统设计与实现。

英文题目：Design and Implementation of an Intelligent Workflow Approval System Based on Large Language Models。

## 1.2 课题来源与类型

本课题来源于企业审批流程数字化与低代码流程设计的实际需求，属于综合性软件工程实践课题。课题以 FlowMind 系统为实现载体，在传统工作流管理、可视化 BPMN 建模和动态表单的基础上，引入大语言模型、智能体工具调用、结构化输出、确定性校验和可观测评估机制，使非专业用户能够通过自然语言生成或修改可部署的审批流程。

## 1.3 研究对象

研究对象包括审批流程的分类、流程模型、业务表单及其全生命周期管理，重点研究自然语言需求如何安全、可解释地转换为符合 BPMN 2.0 和 VForm3 数据规范的增量设计操作。系统覆盖前端交互、微服务业务处理、流程引擎执行及独立 AI 服务四个方面。

# 二、研究背景与意义

## 2.1 研究背景

请假、报销、采购、合同审核等审批业务广泛存在于企业和公共组织中。传统审批系统虽然能够实现线上流转，但流程建模往往依赖技术人员或熟悉 BPMN 的业务管理员。用户需要理解开始事件、用户任务、排他网关、顺序流、候选角色等概念，还要完成表单字段、权限和条件表达式配置。对于需求频繁变化的中小型组织，这种建设方式存在沟通链条长、修改成本高和上线周期慢等问题。

BPMN 2.0.2 由对象管理组织发布，定义了业务流程模型的图形语义和 XML 交换格式，为不同建模工具和流程引擎之间的互操作提供基础[1]。Flowable 能够部署 BPMN 2.0 流程定义、创建流程实例并管理运行及历史数据[2]。然而，标准化的执行能力并没有直接降低业务人员的建模门槛。

大语言模型具备较强的自然语言理解和内容生成能力。ReAct 方法将推理与外部行动交替组织，使模型能够在生成过程中调用知识库或业务接口获取信息[3]。这为“自然语言描述—检索企业真实目录—生成流程模型”提供了技术基础。但若直接让模型返回完整 BPMN XML 或完整表单 JSON，仍容易出现节点丢失、标识冲突、角色编造、语法错误和全量覆盖等问题。因此，本课题不把大语言模型当作无约束代码生成器，而是将其置于受控的软件工程链路中：模型输出最小增量操作，服务端在原始设计副本上应用操作，再执行语法校验和业务校验，只有通过后才展示变更预览。

## 2.2 理论意义

本课题探索了生成式人工智能与传统工作流系统结合的方法。其核心不是单次文本生成，而是把概率性模型嵌入确定性的状态机、约束模型和验证闭环中。研究可为以下问题提供工程化参考：

1. 如何把自然语言意图映射为可执行的流程领域操作；
2. 如何通过 ReAct 工具检索降低角色、分类和表单引用的幻觉；
3. 如何用结构化输出、规则校验和有限重试约束生成结果；
4. 如何在多轮会话中保持流程上下文并避免覆盖用户已有设计；
5. 如何通过链路追踪和黄金数据集评估持续改进提示词及模型配置。

## 2.3 实践意义

系统完成后，业务用户可用自然语言创建流程分类、审批流程和动态表单，也可针对现有设计提出“在经理审批后增加财务审批”等增量修改要求。候选结果先进入可视化预览，用户确认后才应用，降低错误设计直接进入生产环境的风险。对开发和运维人员而言，统一的模型运行时、Redis 会话状态、Langfuse 链路追踪和可重复评估脚本能够提高故障定位及版本迭代效率。

# 三、国内外研究与应用现状

## 3.1 工作流与低代码流程建模

工作流管理领域已经形成较成熟的建模和执行标准。BPMN 2.0.2 同时提供面向业务人员的图形符号和面向系统交换的 XML 元模型[1]。Flowable 等开源流程引擎围绕流程定义部署、实例启动、任务办理、历史查询及 REST API 提供了工程能力[2]。国内大量政企系统也采用基于 Spring Cloud 的微服务架构，将认证、系统管理、流程引擎和网关拆分部署。现有低代码平台主要通过拖拽设计器降低操作难度，但用户仍需掌握节点语义、连线条件和表单配置规则。

## 3.2 大语言模型智能体与工具调用

ReAct 研究提出让语言模型交替生成推理轨迹和任务行动，行动结果又反过来支持后续推理[3]。与只依赖提示词内部知识的生成方式相比，工具调用可以访问实时、权威的外部数据。本课题将这一思想用于企业目录查询：模型可检索真实流程分类、角色、表单和既有流程模型，不直接编造数据库标识。

LangGraph 提供面向有状态智能体的图式编排能力，重点支持持久化、流式输出和可恢复执行[4]。其 checkpoint 机制可以按 thread 保存每一步图状态，为多轮会话记忆和故障恢复提供基础[5]。这类显式状态机比把全部逻辑写在单个提示词或单个接口函数中更容易观察和测试。

## 3.3 大模型应用的可观测与评估

大模型输出具有概率性，仅依赖传统接口测试难以评估提示词或模型版本变化。Langfuse 等平台使用 trace、observation 和 session 组织模型调用链，并提供数据集、实验与评分能力[6][7]。黄金数据集可以保存真实匿名对话及人工构造的边界用例，通过稳定契约评价生成结果，而不是要求模型文案逐字一致。

## 3.4 现有方案不足

综合现有技术，单项能力已较成熟，但端到端方案仍存在以下不足：

- 自然语言直接生成完整 XML，容易破坏原有扩展属性或图形坐标；
- 模型缺少企业真实目录上下文，可能生成不存在的角色或表单；
- 只做 JSON Schema 校验，无法发现孤立节点、多起点、无结束节点等业务错误；
- 全量覆盖式修改不利于保护用户已有流程；
- 模型切换、提示词调整和生成失败缺少统一追踪与回归基线；
- 流式输出、断线和模型降级处理不当时，前端可能收到重复内容或不完整结果。

本课题拟通过“操作协议 + 双层校验 + 状态机重试 + 用户预览确认 + 全链路观测”解决上述问题。

# 四、研究目标与主要内容

## 4.1 总体目标

设计并实现一个前后端分离、微服务化的智能流程审批系统。系统既具备传统流程管理、任务审批和动态表单能力，又能通过自然语言辅助设计流程分类、BPMN 流程和 VForm3 表单。AI 生成结果必须可追踪、可校验、可回退，且默认不覆盖用户现有设计。

## 4.2 功能目标

1. 实现用户认证、角色权限、流程分类、流程模型、部署、任务办理、审批中心和草稿箱等基础功能；
2. 实现全局 AI 对话助手，支持多轮历史和逐 token 流式输出；
3. 实现分类、流程和表单三类 AI 设计入口；
4. 支持对现有流程和表单进行增量修改，只有用户明确选择全部重新生成并二次确认时才允许全量替换；
5. 对生成的 BPMN XML、VForm3 JSON 和业务引用执行确定性校验；
6. 生成结果先展示变更预览，用户确认后再写入页面正式状态；
7. 实现模型 Provider 降级、错误兜底、提示词版本管理和灰度发布；
8. 接入 Langfuse，实现工作流、模型、工具和评估结果的完整追踪；
9. 建立含单轮、多轮和失败场景的黄金数据集，支持全量或指定用例执行。

## 4.3 研究内容

### 4.3.1 审批业务平台设计

基于 Vue 3 和 Element Plus 实现工作台、流程管理、表单管理、审批中心及 AI 交互界面；基于 Spring Cloud 和 RuoYi-Cloud 实现认证、网关、系统管理及 Flowable 业务服务；使用 MySQL 保存业务数据，使用 Nacos 完成服务注册与配置管理。

### 4.3.2 AI 工作流编排

采用 FastAPI 提供独立 AI 服务，使用 LangGraph 构建 `prepare → design → review → format` 工作流。prepare 节点统一处理请求类型、模式和基线数据；design 节点完成意图分析、工具检索与结构化操作生成；review 节点执行规则校验并按有限预算反馈重试；format 节点形成稳定响应。

### 4.3.3 增量设计协议

针对流程、表单和分类定义具有类型约束的操作集合，包括新增、修改、删除、移动和经授权的整体替换。服务端先深拷贝原设计，再应用操作。BPMN 修改基于原始 XML DOM 合并，保留未涉及的扩展元素、监听器和图形坐标。`add_node.after_id` 自动插入节点并重连顺序流，显式边只补全当前批次生成的裸连线，不覆盖原有同端点条件分支。

### 4.3.4 生成校验与安全兜底

结构层使用 Pydantic 约束模型输出；语法层验证 BPMN XML 和 VForm3 JSON；业务层校验节点数量、起止事件、连线连通性、网关条件、角色引用、分类编码冲突及表单字段规则。可修复错误反馈给模型重试；连续出现相同错误时提前终止，防止死循环。失败结果统一返回 `error` 且不携带可应用草稿，信息不足返回 `needs_input`，成功返回 `ready`。

### 4.3.5 可观测、版本与评估

Langfuse 根 trace 关联用户、会话和业务 trace_id，子 observation 覆盖 LangGraph 节点、ReAct 工具、Provider 尝试和结构化生成。提示词统一保存为 Markdown，通过版本清单和 thread_id 稳定哈希实现灰度。黄金数据集使用 JSONL 管理，记录输入、期望契约和多轮上下文，执行结果写入 Dataset Run。

# 五、拟解决的关键问题

## 5.1 概率性输出与确定性流程规范的矛盾

大语言模型可能输出格式正确但业务错误的内容。拟采用“结构化输出—操作应用—领域校验—错误反馈重试”的闭环，将模型限制在候选方案生成环节，把是否可应用交给确定性规则判断。

## 5.2 增量修改的无损性

若每轮都返回完整模型，旧节点和未知扩展属性可能被遗漏。拟让模型只描述变化，服务端基于原始数据应用最小操作；对 BPMN 使用 DOM 级合并，未提及部分保持不变。全量替换作为同一操作协议中的受控能力，不另设含义重叠的重置功能。

## 5.3 企业真实数据引用

模型不知道系统中已有的角色、分类和表单。拟提供只读检索工具，并通过认证令牌调用 Java 后端权威接口；生成后再次做业务校验，形成“检索降低幻觉、校验阻止漏网错误”的双保险。

## 5.4 流式输出与模型降级一致性

模型在首个 token 前失败时可以安全切换 Provider；一旦已有内容输出，若从备用模型重新开始会造成重复。拟在统一模型运行时记录 `token_started` 状态：首 token 前允许切换，首 token 后中断则结束当前流并返回可追踪错误，不重放内容。

## 5.5 多轮状态与并发安全

拟使用 Redis checkpoint 按 thread 保存 LangGraph 状态，通过会话命名空间隔离不同用户。对同一设计会话使用带 TTL 的分布式锁，避免并发修改互相覆盖，并使用 ownership token 保证释放锁时不会误删后续请求持有的锁。

# 六、系统方案与技术路线

## 6.1 总体架构

系统分为表现层、网关与业务服务层、AI 编排层、流程引擎与数据层、可观测评估层。

```text
用户浏览器
   │
   ▼
Vue 3 前端 ── SSE/HTTP ── Spring Cloud Gateway
   │                              │
   │                              ├─ Auth / System / Flowable
   │                              │          │
   └──────── AI 设计请求 ─────────┤          └─ MySQL
                                  ▼
                         FastAPI + LangGraph
                         prepare → design → review → format
                                  │       │
                   ReAct 检索工具 ┘       └─ BPMN/VForm3/业务校验
                                  │
                       模型 Provider / Redis / Langfuse
```

## 6.2 技术选型

| 层次 | 主要技术 | 选型理由 |
|---|---|---|
| 前端 | Vue 3、Vite、Element Plus | 组件化、响应式，适合管理端和复杂设计器界面[8] |
| 流程设计 | BPMN-JS、VForm3 | 分别承担 BPMN 可视化和动态表单编辑 |
| 网关与业务 | Spring Boot、Spring Cloud、RuoYi-Cloud | 便于服务发现、路由、认证及模块化业务开发[9] |
| 流程引擎 | Flowable | 可部署和执行 BPMN 2.0 定义，提供任务及历史 API[2] |
| AI API | FastAPI、Pydantic | 基于类型注解构建接口并进行数据校验[10] |
| 智能编排 | LangChain、LangGraph | 支持模型工具调用、有状态图编排、持久化与流式执行[4] |
| 状态与锁 | Redis | 保存 checkpoint、会话索引和分布式锁；可按部署需求配置持久化[11] |
| 观测评估 | Langfuse | 支持 trace/session、数据集实验和评分[6][7] |

## 6.3 AI 设计时序

1. 前端携带用户输入、当前设计基线、会话标识和模式发送请求；
2. 网关透传 JWT，AI 服务完成身份校验并建立用户级会话命名空间；
3. prepare 节点标准化基线并拒绝非法设计类型或模式；
4. design 节点先判别设计、追问或回退意图；
5. ReAct 智能体按需调用后端目录检索工具；
6. 独立结构化阶段依据 Pydantic Schema 生成最小操作；
7. 操作应用器在基线副本上物化候选设计；
8. review 节点执行语法和业务校验，不通过则携带 rule_id 反馈重试；
9. format 节点生成 `ready`、`needs_input` 或 `error` 响应；
10. 前端以 SSE 接收进度和最终结果，在设计器中展示预览；
11. 用户确认后应用候选设计，取消则原数据保持不变。

# 七、研究方法

## 7.1 文献研究法

查阅 BPMN 2.0.2 标准、Flowable 引擎文档、LangGraph 持久化机制、ReAct 论文和大模型可观测评估资料，确定领域模型和技术边界。

## 7.2 软件工程方法

采用分层架构和模块化设计，将 API、工作流编排、设计领域、模型运行时、后端集成及基础设施分离。通过接口契约明确 Vue 前端、Java 微服务和 Python AI 服务之间的职责。

## 7.3 实验与测试方法

使用单元测试验证操作应用、BPMN/VForm3 转换、校验规则、模型降级和提示词版本；使用集成测试验证完整工作流；使用系统测试覆盖认证、SSE、真实模型、Redis checkpoint 与固定后端目录数据。利用黄金数据集比较不同提示词和模型版本下的稳定契约得分。

## 7.4 对比分析法

对比“完整结果覆盖”和“增量操作修改”、“纯模型生成”和“检索加校验”、“一次性响应”和“SSE 流式响应”三组方案，从数据安全、可解释性、用户体验和测试可重复性方面分析设计取舍。

# 八、可行性分析

## 8.1 技术可行性

项目所采用的 Vue、Spring Cloud、Flowable、FastAPI、LangGraph、Redis 等均有成熟文档和社区基础。BPMN 2.0 提供标准交换格式，Flowable 可直接部署生成的 XML。现有代码已经形成前端、Java 微服务和 AI 服务三部分，核心链路具备可运行实现，因此技术风险可控。

## 8.2 经济可行性

主体框架与中间件采用开源软件，本地可使用兼容 OpenAI 协议的模型服务，也可按配置接入云端模型。通过 Provider 优先级、最大重试次数和功能开关控制调用成本。系统适合作为本科阶段原型和中小规模组织的二次开发基础。

## 8.3 操作可行性

前端提供可视化流程设计器和表单设计器，AI 结果不会直接覆盖正式数据。用户只需描述业务需求并确认预览，无需掌握 XML。系统保留传统人工编辑能力，因此 AI 不可用时仍可完成核心审批配置。

## 8.4 安全与合规可行性

认证沿用网关 JWT，AI 服务只接收经过认证的用户信息；密钥由环境变量管理，不写入代码；日志与 Langfuse 元数据不记录 API Key。真实对话进入黄金数据集前需要匿名化。对删除、部署等有副作用操作仍由业务端权限和用户确认控制。

# 九、预期创新点

1. **面向流程领域的增量操作协议**：模型输出最小变更，避免完整 JSON/XML 重写造成信息丢失；
2. **概率生成与确定性验证结合**：将 Schema、BPMN/VForm3 语法和业务规则组成多层验证闭环；
3. **企业目录感知的 ReAct 设计**：生成前检索真实角色、分类和表单，生成后再次核验引用；
4. **预览优先的安全交互**：成功结果只是候选变更，必须经用户确认才应用；失败不返回可覆盖草稿；
5. **面向持续迭代的观测评估**：提示词 Markdown 版本、稳定灰度、Langfuse trace 与单轮/多轮黄金数据集形成闭环；
6. **流式场景下的精确降级语义**：首 token 前允许 Provider 切换，输出后禁止重放，兼顾可用性与内容一致性。

# 十二、风险与应对措施

| 风险 | 表现 | 应对措施 |
|---|---|---|
| 模型输出不稳定 | 字段缺失、错误节点、格式不兼容 | 结构化输出、规则校验、有限重试和黄金集回归 |
| 外部模型故障 | 超时、限流或接口差异 | 统一 Provider 适配、能力过滤和可配置降级 |
| 业务数据幻觉 | 引用不存在的角色或表单 | ReAct 查询后端权威数据并二次校验 |
| 增量修改损坏原模型 | 原节点、扩展属性或坐标丢失 | 基于原始 DOM 合并、深拷贝应用、预览确认 |
| 多轮状态冲突 | 并发请求覆盖 checkpoint | 用户会话隔离、Redis 分布式锁和 TTL |
| 评估结果不可复现 | 对话样本和提示词变化 | 稳定用例 ID、提示词版本记录和 Dataset Run |
| 敏感信息泄露 | 密钥或真实对话进入仓库 | `.env` 管理密钥、提交扫描、数据匿名化 |
