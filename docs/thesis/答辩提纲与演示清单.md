# FlowMind 答辩提纲与演示清单

## 1. PPT 建议结构

按学校规定时长调整，建议 10—12 页，每页突出一个结论。

1. 课题名称、学生与导师信息。
2. 问题背景：传统建模门槛与直接生成 XML 的风险。
3. 需求和角色：管理端、申请端、审批端。
4. 系统架构：Nginx、Gateway、Java/Flowable、AI 服务与存储。
5. 关键设计：自然语言 → 真实数据检索 → 结构化操作 → 校验 → 预览确认。
6. 四类 AI 设计入口及一组真实生成结果。
7. 状态与安全：多轮、版本、未保存内容、任务权限与系统变量保护。
8. 业务闭环：发布、申请、审批、结束及历史记录。
9. Langfuse trace、数据集和实验结果，注明真实执行版本。
10. 测试与局限：分开呈现自动回归、人工验收、未执行项目。
11. 本人工作、上游复用与总结展望。

## 2. 现场演示顺序

| 步骤 | 操作 | 展示重点 |
| --- | --- | --- |
| 1 | 登录，进入模型管理 | 管理页面与 OA 分工 |
| 2 | 生成分类和基本信息 | 不只是聊天文本，能够回填业务字段 |
| 3 | 生成表单并调整字段 | 结果仍是可编辑的真实表单 |
| 4 | 生成流程并局部修改 | 节点、审批人及绑定变化可读 |
| 5 | 放弃一次预览，再应用另一变更 | 用户控制最终设计 |
| 6 | 保存发布、另一账号发起、审批人处理 | 工作流真正执行，而不是只画出图 |
| 7 | 查看 trace 或单条实验记录 | 请求、生成与错误可追踪 |

现场模型调用存在网络和时延风险。提前准备同一交付版本的脱敏截图、录屏及已发布流程，注明是备份演示；不能把备份冒充当场成功执行。

## 3. 常见答辩问题

**与普通审批系统相比增加了什么？**

重点不是替代 Flowable，而是把自然语言转换为可审查的设计操作，并接入已有业务数据、校验与可视化设计器。

**为什么不直接让模型输出 BPMN XML？**

已有模型有节点 ID、扩展配置和布局。结构化操作更便于限制修改范围、检查引用和展示差异；全量替换仍需明确意图及预览确认。

**模型生成错误怎么办？**

通过结构与业务校验、错误反馈、澄清和人工预览降低风险，但不能保证业务语义总是正确。失败时不得伪造成功或覆盖原设计。

**如何计算通过率？**

按明确分母分别计算状态/输出契约通过率与人工业务验收通过率。追问可以是合理交互，但不能算作目标流程完成；没有实测数据不报告准确率或性能提升。

**为什么 webhook 返回成功却没有实验？**

202 只代表已接收。实际执行还依赖有效令牌、数据集、模型和网络，需要查看后台结果与 Langfuse Dataset Run。

**哪些是本人完成，哪些来自开源项目？**

据实区分 RuoYi 管理框架、Flowable 引擎、BPMN-JS/VForm3 设计器与实际完成的 AI 集成、校验、预览、权限、测试工作；引用项目来源并说明改造范围。
